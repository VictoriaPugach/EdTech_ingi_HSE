# Использование Node.js для Realtime Sync Service

Дата создания: 12.01.2026
Статус: Принято

## Контекст

Realtime Sync Service отвечает за поддержание WebSocket-соединений со всеми участниками активных сессий, прием и рассылку CRDT-обновлений, управление awareness-состоянием и хранение авторитетного снапшота Y.Doc в памяти. Требование: p95-задержка синхронизации менее 100 мс при 10 одновременных пользователях. В учебном контексте типичная нагрузка составляет 2-12 участников на сессию, несколько параллельных сессий.

## Рассмотренные варианты

Go обеспечивает высокую производительность и эффективное управление памятью при большом числе горутин. Однако у Go нет официального Yjs-совместимого CRDT-провайдера. Реализация сервера, совместимого с y-websocket, потребовала бы написания собственного обработчика протокола Yjs, что существенно увеличивает объем работы.

Python AsyncIO обеспечивает асинхронную обработку WebSocket-соединений. Однако GIL ограничивает параллельное выполнение в CPU-интенсивных операциях. Python-реализация серверного Yjs-провайдера не имеет официальной поддержки.

Node.js с event loop оптимален для большого числа одновременных I/O-интенсивных соединений. Пакет y-websocket предоставляет готовый серверный провайдер, совместимый с Yjs-клиентом. Пакет y-redis обеспечивает интеграцию с Redis для распределения обновлений между несколькими нодами. Стек полностью совместим с TypeScript.

## Решение

Realtime Sync Service реализован на Node.js 20 LTS с TypeScript. Транспортный слой построен на библиотеке y-websocket или uWebSockets.js в зависимости от финальных результатов нагрузочного тестирования. Для каждой активной сессии на сервере хранится экземпляр Y.Doc. Входящие обновления применяются к Y.Doc и публикуются в Redis Pub/Sub канал сессии для рассылки другим нодам.

## Обоснование

Единственное техническое обоснование выбора Node.js относительно остальных рантаймов: y-websocket и y-redis официально поддерживаются командой Yjs и реализованы именно для Node.js. Использование иного рантайма потребовало бы написания собственного провайдера с реализацией протокола Yjs, что вышло бы за рамки MVP.

Event-driven модель Node.js подходит для данного типа нагрузки. Realtime Sync Service почти полностью I/O-bound: принять байты от клиента, применить к Y.Doc, сериализовать обновление, отправить остальным. CPU-интенсивные операции (анализ кода, генерация подсказок) выполняются в отдельном Hint Service.

Node.js 20 LTS выбран для стабильности и гарантированной долгосрочной поддержки в период разработки и эксплуатации MVP.

Горизонтальное масштабирование обеспечивается через Redis Pub/Sub: несколько нод одного сервиса могут обслуживать участников одной сессии, получая обновления через общий Redis-канал.

## Последствия

Realtime Sync Service хранит состояние Y.Doc в памяти. При перезапуске контейнера состояние восстанавливается из Redis-снапшота. Время восстановления определяется размером снапшота и не должно превышать нескольких секунд при типичном объеме учебного проекта.

Node.js не подходит для CPU-интенсивных задач без использования worker_threads. Если в Realtime Sync Service появятся задачи с длительными вычислениями, их необходимо перенести в отдельный worker или в Hint Service.

## Риски

При очень большом числе соединений (сотни одновременных сессий) стандартные WebSocket-библиотеки Node.js могут стать узким местом по сравнению с uWebSockets.js. Снижение риска: нагрузочное тестирование k6 на целевой нагрузке до финализации библиотеки.

## Оценка результативности

Сервис считается корректно реализованным, если при 10 одновременных пользователях в одной сессии p95-задержка между отправкой CRDT-обновления одним клиентом и получением остальными не превышает 100 мс, и если после перезапуска контейнера клиенты восстанавливают соединение и получают актуальное состояние Y.Doc.
