# Использование WebSocket для синхронизации CRDT в реальном времени

Дата создания: 08.01.2026
Статус: Принято

## Контекст

Совместное редактирование кода требует низкой задержки доставки обновлений между клиентами. Каждая операция редактирования, вставка или удаление символа, должна быть доставлена остальным участникам сессии как можно быстрее. Соединение между клиентом и сервером существует на протяжении всей активной сессии, которая может длиться от нескольких минут до нескольких часов. Awareness-обновления (курсоры, состояние присутствия) отправляются несколько раз в секунду.

## Рассмотренные варианты

HTTP Long Polling. Клиент периодически опрашивает сервер на предмет новых обновлений. Добавляет задержку, пропорциональную интервалу опроса. Создает избыточную нагрузку на сервер из-за множества HTTP-запросов без новых данных. Не подходит для требования p95 < 100 мс.

Server-Sent Events (SSE). Обеспечивает однонаправленный поток от сервера к клиенту. Обновления от клиента к серверу по-прежнему требуют отдельных HTTP-запросов. Не подходит для двунаправленного обмена CRDT-обновлениями.

WebRTC Data Channel. Подходит для P2P-коммуникации, но требует сигналинг-сервера для установки соединения и NAT traversal. Архитектура P2P усложняет хранение авторитетного состояния Y.Doc на сервере и восстановление состояния при подключении нового участника.

WebSocket. Обеспечивает полнодуплексное соединение с низкой задержкой поверх единого TCP-соединения. Нативно поддерживается всеми современными браузерами. y-websocket реализует протокол обмена Yjs-обновлениями поверх WebSocket без дополнительных зависимостей.

## Решение

Realtime Sync Service принимает WebSocket-соединения по протоколу WSS (WebSocket Secure). Каждое соединение аутентифицируется: JWT передается в параметре строки подключения и верифицируется при установке соединения. После успешной проверки клиент присоединяется к комнате сессии.

Два типа сообщений передаются по одному WebSocket-соединению: CRDT-обновления Y.Doc в бинарном формате Yjs и awareness-обновления в формате Yjs Awareness Protocol. Разделение типов сообщений реализовано на уровне протокола y-websocket.

Ping/pong heartbeat настроен для обнаружения разрывов соединения. При разрыве клиент применяет экспоненциальную задержку перед переподключением и передает накопленные офлайн-обновления при восстановлении.

## Обоснование

WebSocket является единственным стандартным протоколом для двунаправленной real-time коммуникации в браузере с поддержкой бинарного формата и приемлемой задержкой. Для требования p95 < 100 мс нет практической альтернативы в браузерном контексте.

WSS (WebSocket поверх TLS) обязателен по требованию безопасности. Все соединения должны использовать шифрование. Nginx Ingress выполняет TLS-терминацию и проксирует соединение к сервису.

Аутентификация при установке соединения, а не при каждом сообщении, снижает накладные расходы. После проверки JWT при подключении сервер считает все сообщения в этом соединении аутентифицированными.

Бинарный формат обновлений Yjs снижает объем передаваемых данных по сравнению с JSON. Каждое обновление содержит только изменение, а не полное состояние документа.

## Последствия

Долгоживущие WebSocket-соединения требуют настройки лимитов на уровне Nginx Ingress и Kubernetes. Таймаут соединения должен быть достаточно большим для активных сессий.

При горизонтальном масштабировании Realtime Sync Service балансировщик нагрузки должен поддерживать sticky sessions или использовать Redis Pub/Sub для синхронизации между нодами. Выбранный подход через Redis Pub/Sub описан в отдельном ADR.

## Риски

Корпоративные прокси-серверы или сети учебных заведений могут блокировать WebSocket-соединения. Снижение риска: использование стандартного порта 443 и WSS, который выглядит как обычный HTTPS. Socket.IO предоставляет fallback на Long Polling, но добавляет размер бандла. Для MVP fallback не реализуется, проблема документируется как известное ограничение.

## Оценка результативности

Протокол считается корректно реализованным, если WebSocket-соединение устанавливается за время менее 500 мс, при разрыве и восстановлении соединения накопленные офлайн-обновления передаются без потерь, и все соединения используют WSS.
