# Выбор Yjs в качестве CRDT-библиотеки

Дата создания: 28.12.2025
Статус: Принято

## Контекст

После принятия решения о применении CRDT для совместного редактирования необходимо выбрать конкретную библиотеку. Требования к библиотеке: поддержка текстового типа данных с CRDT-семантикой, интеграция с редактором кода CodeMirror 6, работа в браузере и на сервере Node.js, бинарный формат обмена обновлениями для минимизации трафика, поддержка awareness-протокола для отображения курсоров и присутствия участников.

## Рассмотренные варианты

Automerge является зрелой CRDT-библиотекой с поддержкой произвольных JSON-документов. Версия Automerge 2 написана на Rust и компилируется в WASM, что обеспечивает высокую производительность. Однако биндинг для CodeMirror 6 официально не поддерживается, реализация потребовала бы написания собственного провайдера. Размер WASM-модуля добавляет нагрузку на загрузку страницы.

ShareDB реализует OT, а не CRDT, и не подходит для выбранного подхода.

Diamond Types представляет собой новую CRDT-реализацию на Rust/WASM с акцентом на минимальный размер истории. Библиотека активно развивается, но экосистема интеграций значительно меньше, чем у Yjs.

Yjs является де-факто стандартом для browser-based CRDT-редакторов. Библиотека написана на JavaScript, работает в браузере и Node.js без дополнительной компиляции. Для CodeMirror 6 существует официально поддерживаемый пакет y-codemirror.next. Для WebSocket-транспорта существует y-websocket. Awareness-протокол встроен в ядро. Бинарный формат обмена основан на кастомной кодировке и компактен по размеру.

## Решение

Используется Yjs. Текстовый тип данных представлен Y.Text, привязанный к CodeMirror 6 через y-codemirror.next. Транспорт обновлений реализован через y-websocket с серверным провайдером на Node.js. Awareness-состояние (курсоры, имена пользователей, цвета) передается через встроенный awareness-канал Yjs отдельно от потока документа.

## Обоснование

Официальный биндинг y-codemirror.next исключает необходимость написания собственного провайдера для редактора. Это снижает риски реализации и объем кода, который нужно поддерживать в рамках MVP.

Единый стек JavaScript/TypeScript для клиента и серверного провайдера упрощает разработку и отладку. Yjs работает в Node.js без WASM, что устраняет проблемы с размером бандла и совместимостью сред выполнения.

Экосистема Yjs включает провайдеры для Redis (y-redis), что необходимо для распределения обновлений между несколькими нодами Realtime Sync Service. Провайдер y-redis позволяет хранить авторитетный снапшот Y.Doc в Redis и синхронизировать состояние между нодами через Pub/Sub.

Awareness-протокол Yjs передает эфемерное состояние, такое как позиция курсора, имя участника и цвет, по отдельному каналу без смешения с CRDT-потоком документа. Это предотвращает рост размера документа из-за накопления awareness-данных.

Сообщество Yjs активно поддерживает библиотеку. Использование в продуктах Notion-like редакторов и нескольких публичных платформах снижает риск прекращения поддержки.

## Последствия

Формат хранения снапшотов Y.Doc зафиксирован в кодировке Yjs. При необходимости миграции на другую CRDT-библиотеку потребуется конвертация всех хранимых снапшотов. На этапе MVP это принятый компромисс.

Версия Yjs фиксируется в package.json. Минорные обновления применяются после проверки обратной совместимости формата обновлений, так как изменение внутреннего формата нарушило бы совместимость клиентов и серверного провайдера.

## Риски

Потенциальный риск связан с производительностью операций Y.Text при очень больших документах. Для типичных учебных задач и объема кода в рамках одной сессии этот риск несущественен. При необходимости работы с крупными файлами можно использовать фрагментацию документа на несколько Y.Text.

## Оценка результативности

Интеграция считается успешной, если тесты на конвергенцию Y.Doc при одновременных вставках и удалениях проходят в 100 процентах случаев, a awareness-обновления отображаются у всех участников сессии без заметной задержки.
