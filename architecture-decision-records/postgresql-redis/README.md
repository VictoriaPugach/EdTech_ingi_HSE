# Выбор PostgreSQL и Redis для хранения данных

Дата создания: 03.02.2026
Статус: Принято

## Контекст

Система хранит несколько категорий данных с разными требованиями. Данные пользователей, сессий, проектов и снапшотов требуют долгосрочного хранения, целостности и поддержки транзакций. Состояние Y.Doc активной сессии должно быть доступно нескольким нодам Realtime Sync Service без обращения к реляционной БД на каждом обновлении. История подсказок и аналитические события хранятся для анализа качества и доработки справочника шаблонов.

## Рассмотренные варианты

MongoDB как основное хранилище. Гибкость схемы избыточна для данных пользователей и сессий с четкой структурой. ACID-транзакции на уровне нескольких документов доступны с версии 4.0, но являются дополнительным усложнением. Отношения между сущностями (пользователь, сессия, проект, участник) естественно выражаются реляционной моделью.

CockroachDB или YugabyteDB как распределенные SQL-базы. Избыточная сложность для MVP: распределенные транзакции, настройка топологии. Для текущего масштаба вертикального масштабирования PostgreSQL достаточно.

PostgreSQL как основная СУБД и Redis как in-memory хранилище для эфемерных данных. PostgreSQL обеспечивает ACID-транзакции, строгую схему, индексы и JSONB для гибких полей. Redis обеспечивает Pub/Sub для CRDT-рассылки, хранение snapshotов Y.Doc для быстрого восстановления и кэширование часто запрашиваемых данных.

## Решение

PostgreSQL 16 используется как основная СУБД. Redis 7 используется как вспомогательное хранилище для трех задач: хранение авторитетного снапшота Y.Doc каждой активной сессии, Pub/Sub-канал для рассылки CRDT-обновлений между нодами Realtime Sync Service, кэширование метаданных сессии и списка участников.

Основные таблицы PostgreSQL: users, sessions, projects, session_participants, snapshots, hint_requests, hints, error_events, achievements, analytics_events.

Правило разделения данных: документ Y.Doc в Redis является рабочей копией для активных сессий. При завершении сессии или по расписанию снапшот сохраняется в таблицу snapshots в PostgreSQL. Redis не является источником истины для долгосрочных данных.

## Обоснование

PostgreSQL выбран из-за реляционной природы основных сущностей. Пользователь связан с сессиями через session_participants, сессии связаны с проектами, снапшоты привязаны к сессиям. Foreign key constraints обеспечивают ссылочную целостность без дополнительной логики в приложении.

ACID-транзакции PostgreSQL необходимы при создании сессии: нужно атомарно создать запись session, запись в session_participants для создателя и опциональные записи для приглашенных участников. Без транзакции возможно создание неполной записи сессии.

JSONB-поля PostgreSQL используются для хранения конфигурации сессии, настроек пользователя и метаданных подсказок, которые имеют переменную структуру. Это позволяет не создавать избыточные таблицы для редко используемых атрибутов при сохранении возможности индексации и запросов.

Redis выбран для снапшотов Y.Doc и Pub/Sub по трем причинам. Первая: операции с Y.Doc требуют низкой задержки, обращение к PostgreSQL на каждый CRDT-update увеличило бы время обработки. Вторая: Pub/Sub Redis нативно поддерживается y-redis и обеспечивает рассылку между нодами без дополнительной инфраструктуры очередей. Третья: эфемерность данных снапшота соответствует модели хранения Redis: при сбое Redis состояние восстанавливается из последнего снапшота в PostgreSQL.

## Последствия

Redis не настроен на постоянное хранение данных (persistence off или RDB-только). При полном отказе Redis состояние активных сессий восстанавливается из последнего снапшота в PostgreSQL с возможной потерей нескольких последних обновлений. Частота периодического снапшотирования в PostgreSQL определяет допустимое окно потери.

Разделение ответственности между PostgreSQL и Redis требует явной документации: какие данные хранятся где и как разрешаются конфликты при восстановлении.

## Риски

При очень большом числе активных сессий объем оперативной памяти Redis может стать ограничением. Снижение риска: настройка максимального TTL для снапшотов неактивных сессий и их вытеснение из Redis после завершения.

Миграции схемы PostgreSQL требуют осторожности в production. Снижение риска: использование инструмента миграций (Flyway или аналог) с явной нумерацией версий схемы.

## Оценка результативности

Решение считается корректно реализованным, если транзакционные операции создания сессий не приводят к несогласованности данных при одновременных запросах, Y.Doc восстанавливается корректно после перезапуска Realtime Sync Service, и нагрузочные тесты не выявляют Redis как узкое место при целевой нагрузке.
