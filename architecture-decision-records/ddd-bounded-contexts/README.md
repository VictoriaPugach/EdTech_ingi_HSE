# Применение DDD с тремя ограниченными контекстами

Дата создания: 16.12.2025
Статус: Принято

## Контекст

Платформа решает три принципиально разные задачи: обеспечение совместного редактирования кода в реальном времени, педагогический анализ кода и генерация подсказок, управление пользователями и учебными сессиями. У каждой задачи свои понятия, ограничения и требования к производительности. Без явного разделения понятий между задачами возникают смешение доменных моделей и неконтролируемые зависимости.

## Рассмотренные варианты

Единая доменная модель без разделения на контексты. Все сущности и логика находятся в общем пространстве имен. При росте кодовой базы это приводит к тому, что изменение логики подсказок затрагивает код CRDT-синхронизации, понятие Session используется по-разному в разных частях системы.

Разделение на микросервисы без явных границ контекстов. Физическое разделение без концептуального не решает проблему смешения понятий: сервисы начинают разделять доменные модели через общие библиотеки.

Domain-Driven Design с тремя ограниченными контекстами: Collaborative Editing, Pedagogical Analysis, Learning Management. Каждый контекст имеет собственный Ubiquitous Language, собственные доменные модели и явно определенные точки интеграции с другими контекстами.

## Решение

Система разделена на три ограниченных контекста.

Bounded Context 1: Collaborative Editing. Ответственность: совместное редактирование кода, CRDT-синхронизация, управление состоянием документа, awareness. Ключевые понятия: Document, Y.Doc, Update, Snapshot, Participant, Cursor. Реализован в Realtime Sync Service на Node.js.

Bounded Context 2: Pedagogical Analysis. Ответственность: анализ кода, классификация ошибок, генерация адаптивных подсказок. Ключевые понятия: CodeSnapshot, SyntaxError, Hint, HintTemplate, ErrorPattern, AnalysisResult. Реализован в Hint Service на Python.

Bounded Context 3: Learning Management. Ответственность: управление пользователями, сессиями, проектами, прогрессом, ролями. Ключевые понятия: User, Role, Session, Project, Achievement, InviteCode, AnalyticsEvent. Реализован в API Gateway/LMS на Node.js.

Правила взаимодействия между контекстами: нет прямых импортов доменных моделей одного контекста в другой. BC-3 является организующим контекстом: создает и хранит записи сессий, управляет их жизненным циклом. BC-1 потребляет идентификатор сессии и данные аутентификации из JWT, но не зависит от доменных моделей BC-3. BC-2 получает только снимок кода и тип ошибки, не зная ничего о пользователях и сессиях.

Anti-Corruption Layer реализован в API Gateway: входящие запросы от клиентов транслируются в команды соответствующего контекста.

## Обоснование

Разные требования к производительности обоснованы разделением контекстов. BC-1 оптимизирован под минимальную задержку CRDT-синхронизации. BC-2 может работать асинхронно с задержкой до 2000 мс. BC-3 управляет транзакционными операциями с PostgreSQL. Смешение этих требований в единой модели привело бы к компромиссам, ухудшающим каждую из задач.

Понятие Session означает разное в разных контекстах. В BC-1 сессия это активный Y.Doc с множеством WebSocket-соединений и awareness-состоянием. В BC-3 сессия это запись в таблице sessions с метаданными, участниками и настройками. DDD позволяет использовать одно слово с разным смыслом в разных контекстах без путаницы, так как контексты явно разделены.

Независимость BC-2 от данных пользователей обеспечивает безопасность: Hint Service получает только код и описание ошибки без персональных данных. Это снижает риски при работе с внешним LLM API.

## Последствия

Карта контекстов фиксируется как архитектурный документ. При добавлении новых функций необходимо явно определять, в какой контекст они входят, и обновлять карту.

Интеграционные тесты должны проверять контракты между контекстами: формат запроса к Hint Service, формат ответа, JWT-payload. Нарушение контракта должно обнаруживаться на уровне интеграционных тестов, а не в production.

## Риски

Нечеткие границы контекстов при разработке приводят к тому, что разработчик добавляет зависимость напрямую между контекстами для скорости реализации. Снижение риска: code review с явной проверкой границ контекстов, запрет cross-context импортов на уровне linting-правил.

## Оценка результативности

Декомпозиция считается корректной, если анализ зависимостей кодовой базы не выявляет прямых импортов типов между контекстами, изменение шаблонов подсказок в BC-2 не требует изменений в BC-1, и добавление нового типа пользовательской роли в BC-3 не затрагивает код BC-1 и BC-2.
