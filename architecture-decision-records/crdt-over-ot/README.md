# Выбор CRDT вместо OT для механизма совместного редактирования

Дата создания: 22.12.2025
Статус: Принято

## Контекст

Платформа обеспечивает совместное редактирование кода нескольких участников в рамках одной сессии. Ученики и преподаватель редактируют один документ одновременно через браузерные клиенты, соединенные с сервером по WebSocket. При разрыве соединения клиент должен накапливать операции локально и применять их после восстановления без потери данных и без ручного разрешения конфликтов.

Среднее число участников сессии составляет от 2 до 12 человек. Нефункциональное требование по задержке синхронизации: p95 < 100 мс при 10 одновременно подключенных пользователях.

## Рассмотренные варианты

Operational Transformation применяется в Google Docs, Quill и ряде других редакторов. OT корректно работает при централизованной координации через сервер, который упорядочивает и трансформирует операции. При множественных одновременных операциях без строгого централизованного упорядочивания корректность трансформаций сложно гарантировать, а алгоритм трансформации становится нетривиальным при наличии более двух клиентов. Реализация OT для произвольного числа клиентов исторически была источником трудно воспроизводимых конфликтов.

Conflict-free Replicated Data Types дают математическую гарантию конвергенции: независимо от порядка применения операций на разных репликах итоговое состояние документа одинаково. CRDT не требует трансформации операций и не зависит от строгого упорядочивания через сервер. Клиент может накапливать обновления офлайн и применять их при восстановлении соединения.

## Решение

Для механизма совместного редактирования выбраны CRDT. Конкретная реализация построена на библиотеке Yjs, которая реализует тип данных Y.Doc и операции вставки и удаления в виде CRDT-обновлений. Обновления передаются по WebSocket в бинарном формате. Сервер хранит Y.Doc в оперативной памяти, применяет входящие обновления и рассылает их остальным участникам через Redis Pub/Sub.

## Обоснование

CRDT снимает требование строгого упорядочивания операций на сервере. Каждый клиент применяет обновления локально немедленно, без ожидания подтверждения от сервера. Это снижает субъективно ощущаемую задержку, так как ввод пользователя отображается сразу, а синхронизация происходит асинхронно.

Офлайн-устойчивость обеспечивается автоматически свойством CRDT: клиент накапливает обновления в Y.Doc локально и при восстановлении соединения передает дифференциальный снимок. Сервер применяет обновление, и документ конвергирует без ручного разрешения конфликтов. Это напрямую закрывает нефункциональное требование о восстановлении без потери данных.

Масштабирование реального времени при CRDT проще, чем при OT. Сервер не является арбитром порядка операций, а лишь транслятором обновлений между клиентами. Это позволяет запускать несколько нод Realtime Sync Service за балансировщиком и использовать Redis Pub/Sub для распределения обновлений между нодами без нарушения семантики.

Развитая экосистема Yjs и наличие готовых биндингов для CodeMirror 6 снижают риски реализации на этапе MVP.

## Последствия

Документ Y.Doc хранится в памяти каждой ноды Realtime Sync Service и в Redis. При перезапуске ноды состояние восстанавливается из Redis-snapshot. Снапшоты периодически сохраняются в PostgreSQL для долгосрочного хранения истории и возможности отката.

Размер Y.Doc растет по мере накопления истории операций, так как CRDT хранит томбстоны удаленных символов. Для ограничения размера документа применяется периодическое сжатие снапшота через Yjs garbage collection.

OT не рассматривается для возможного использования в будущем. Переход между алгоритмами потребовал бы полной миграции формата хранения документов.

## Риски

Основной операционный риск: рост размера Y.Doc при интенсивном редактировании без регулярного сжатия. Снижение риска: периодический GC-цикл Yjs с последующим snapshot в Redis и PostgreSQL.

При сетевом разделении нескольких нод без доступа к Redis клиенты, подключенные к разным нодам, временно расходятся. После восстановления связи Redis-состояние используется как авторитетный снапшот, и ноды синхронизируются. Временная несогласованность в этом сценарии допустима в рамках уровня надежности MVP.

## Оценка результативности

Выполнение критерия считается подтвержденным, если в нагрузочных тестах при 10 одновременных пользователях p95-задержка синхронизации не превышает 100 мс, все CRDT-тест-кейсы на конвергенцию проходят, и после разрыва соединения ни одна операция не теряется.
