# CI/CD pipeline на GitHub Actions

Дата создания: 20.03.2026
Статус: Принято

## Контекст

Проект содержит несколько независимых компонентов: Frontend на TypeScript, Realtime Sync Service на Node.js, API Gateway на Node.js, Hint Service на Python. Каждое изменение в кодовой базе должно автоматически проходить проверку: запуск тестов, статический анализ, сборку образов и деплой в test-окружение. Ручной деплой в production должен требовать явного действия.

## Рассмотренные варианты

Jenkins. Требует собственного сервера, администрирования, настройки агентов. Для учебного проекта избыточные операционные издержки.

GitLab CI. Полноценная альтернатива, но проект размещен на GitHub. Переезд ради CI нецелесообразен.

CircleCI, Travis CI. Платные при значимой нагрузке. Меньшая интеграция с GitHub-экосистемой.

GitHub Actions. Нативная интеграция с GitHub-репозиторием, бесплатный лимит для публичных репозиториев, готовые Actions для Docker, Kubernetes, Yandex Cloud. Конфигурация хранится в репозитории под системой контроля версий.

## Решение

CI/CD реализован на GitHub Actions. Конфигурация находится в директории .github/workflows/.

Pipeline состоит из трех стадий:

CI (запускается при каждом push и pull request):
- lint и type-check для TypeScript-компонентов;
- unit и integration тесты через Vitest (Frontend, API Gateway) и Pytest (Hint Service);
- статический анализ через SonarQube (опционально при наличии токена);
- сборка Docker-образов без push для проверки корректности Dockerfile.

CD Test (запускается при push в ветку main):
- сборка и публикация Docker-образов в Yandex Container Registry с тегом по SHA коммита;
- применение Kubernetes-манифестов к namespace test через kubectl;
- запуск smoke-тестов против test-окружения.

CD Production (запускается вручную через workflow_dispatch или при создании тега vX.Y.Z):
- применение манифестов к namespace production с явным подтверждением;
- уведомление о завершении деплоя.

Секреты (ключи доступа к Yandex Cloud, Container Registry, SonarQube) хранятся в GitHub Secrets репозитория.

## Обоснование

Автоматический запуск CI при каждом pull request гарантирует, что изменения не нарушают тесты до слияния в main. Это снижает риск введения регрессий при параллельной разработке нескольких компонентов.

Разделение автоматического деплоя в test и ручного деплоя в production соответствует стандартной практике для проектов с реальными пользователями. Случайный деплой сломанной версии в production исключен.

GitHub Actions поддерживает matrix-стратегию для параллельного запуска тестов в нескольких компонентах, что сокращает общее время CI-прогона.

Хранение конфигурации pipeline в репозитории обеспечивает версионирование и аудит изменений в CI/CD как части кодовой базы.

## Последствия

При добавлении нового компонента необходимо обновить CI-workflow: добавить соответствующий job для тестов и сборки образа. Это явная задача, которая не может быть пропущена незаметно.

Время полного прогона CI должно оставаться разумным. Для MVP целевое время: менее 10 минут. При росте числа тестов параллельный запуск через matrix сохраняет время прогона в приемлемых пределах.

## Риски

Исчерпание бесплатного лимита GitHub Actions при интенсивной разработке. Снижение риска: кэширование зависимостей (node_modules, pip cache) в Actions для ускорения прогона и снижения числа billable минут.

Компрометация GitHub Secrets при неправильном обращении. Снижение риска: запрет вывода секретов в логи, использование OIDC-аутентификации для Yandex Cloud вместо долгоживущих ключей при наличии поддержки.

## Оценка результативности

Pipeline считается корректно настроенным, если каждый pull request получает результат CI до ревью, деплой в test-окружение происходит автоматически после слияния в main, и деплой в production требует явного ручного действия.
