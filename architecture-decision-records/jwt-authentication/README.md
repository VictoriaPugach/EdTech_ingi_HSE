# Использование JWT для аутентификации пользователей

Дата создания: 10.02.2026
Статус: Принято

## Контекст

Платформа поддерживает три типа пользователей: ученик, преподаватель и администратор. Каждый запрос к REST API и каждое WebSocket-соединение должны содержать подтвержденную идентичность пользователя. Система состоит из нескольких независимых сервисов: API Gateway/LMS, Realtime Sync Service, Hint Service. Хранение централизованных сессий потребовало бы обращения к базе данных или Redis при каждом запросе от каждого сервиса.

## Рассмотренные варианты

Серверные сессии на основе cookies. Требуют централизованного хранилища сессий (обычно Redis) и обращения к нему при каждом запросе. При нескольких нодах Realtime Sync Service необходимы sticky sessions или shared Redis-хранилище сессий. Мобильные и WebSocket-клиенты работают с cookie-сессиями менее естественно.

OAuth 2.0 с собственным authorization server. Предоставляет полноценную модель делегированного доступа с refresh-токенами. Добавляет значительную сложность: отдельный authorization server, управление refresh-токенами, дополнительные HTTP-запросы при обновлении. Избыточно для MVP с единственным провайдером идентичности.

JWT как stateless токен. Содержит идентификатор пользователя, email, роль и срок действия. Подписывается секретным ключом. Любой сервис проверяет подпись без обращения к внешнему хранилищу. Время проверки составляет доли миллисекунды.

## Решение

Используются JWT, подписанные алгоритмом HS256. Токен выдается при успешной аутентификации в API Gateway и содержит поля: sub (идентификатор пользователя), email, role (student/teacher/admin), exp (время истечения). Срок жизни токена составляет 24 часа. Токен передается клиентом в заголовке Authorization: Bearer при REST-запросах и в параметре строки подключения при WebSocket-соединении.

Каждый сервис верифицирует JWT самостоятельно, используя общий секрет из переменной окружения. Межсервисные вызовы от API Gateway к Hint Service не требуют передачи пользовательского JWT, так как выполняются в доверенной внутренней сети.

## Обоснование

Stateless природа JWT исключает необходимость общего хранилища сессий между сервисами. Realtime Sync Service проверяет токен при установке WebSocket-соединения без обращения к API Gateway или базе данных. Это снижает задержку при подключении и устраняет зависимость Realtime Sync Service от доступности API Gateway во время активной сессии.

Включение роли пользователя в payload токена позволяет проверять права доступа локально в каждом сервисе без дополнительных запросов. Преподаватель имеет право создавать сессии и добавлять комментарии, ученик только редактирует код. Эти проверки выполняются в middleware каждого сервиса.

Простота реализации JWT соответствует масштабу MVP. Библиотеки для верификации JWT доступны как для Node.js (jsonwebtoken), так и для Python (python-jose или PyJWT), что обеспечивает единообразную верификацию во всех сервисах.

## Последствия

JWT не может быть отозван до истечения срока действия без дополнительной инфраструктуры. Если аккаунт пользователя нужно заблокировать немедленно, текущий токен останется валидным до exp. Для MVP это принятое ограничение. При необходимости немедленного отзыва можно реализовать blacklist в Redis, но это частично нивелирует преимущества stateless подхода.

Короткий срок жизни токена (24 часа) снижает окно риска при компрометации. Клиент должен пройти повторную аутентификацию при истечении токена.

Секретный ключ подписи JWT хранится в переменной окружения и не попадает в систему контроля версий. В production используется Kubernetes Secret.

## Риски

Компрометация секретного ключа позволит создавать валидные токены для любых пользователей. Снижение риска: ротация ключа при подозрении на компрометацию с аннулированием всех текущих токенов, хранение ключа в Kubernetes Secret.

Алгоритм HS256 использует симметричный ключ. Если потребуется передать возможность верификации токенов третьей стороне без раскрытия секрета, потребуется переход на RS256. Для MVP этого не требуется.

## Оценка результативности

Аутентификация считается корректно реализованной, если все запросы без валидного токена возвращают HTTP 401, запросы с токеном с истекшим сроком возвращают HTTP 401, проверка прав на основе роли работает корректно во всех сервисах, и время верификации токена не превышает 1 мс.
