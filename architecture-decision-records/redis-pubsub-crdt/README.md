# Использование Redis Pub/Sub для распределения CRDT-обновлений между нодами

Дата создания: 18.01.2026
Статус: Принято

## Контекст

Realtime Sync Service масштабируется горизонтально: несколько нод могут одновременно обслуживать клиентов одной сессии. Участники сессии, подключенные к разным нодам, должны получать одни и те же CRDT-обновления. Без общего канала рассылки ноды работают изолированно: обновление от клиента A, подключенного к ноде 1, не попадет к клиенту B на ноде 2.

## Рассмотренные варианты

Прямые соединения между нодами по принципу gossip или mesh. Требуют динамического обнаружения нод, управления соединениями между нодами, сложной логики маршрутизации. Избыточная сложность для MVP.

Kafka или RabbitMQ как брокер сообщений. Kafka обеспечивает высокую пропускную способность и хранение истории сообщений. Для рассылки CRDT-обновлений история не нужна, а операционная сложность Kafka несоразмерна задаче. RabbitMQ добавляет дополнительный компонент инфраструктуры без существенных преимуществ перед Redis в данном сценарии.

Redis Pub/Sub. Redis уже используется в системе для хранения снапшотов Y.Doc. Pub/Sub нативно поддерживается Redis без дополнительных компонентов. Пакет y-redis реализует интеграцию Yjs с Redis Pub/Sub и поддерживает авторитетное хранение Y.Doc в Redis с синхронизацией между нодами.

## Решение

Каждой сессии соответствует Redis Pub/Sub канал с именем вида session:{sessionId}. Когда нода Realtime Sync Service принимает CRDT-обновление от клиента, она применяет его к локальному Y.Doc, публикует обновление в Redis-канал сессии и рассылает его подключенным к этой ноде клиентам. Остальные ноды, подписанные на тот же канал, получают обновление и рассылают его своим клиентам.

Авторитетный снапшот Y.Doc хранится в Redis по ключу ydoc:{sessionId}. Новая нода при старте загружает снапшот из Redis и подписывается на канал.

## Обоснование

Использование Redis для двух задач, хранения снапшотов и Pub/Sub рассылки, позволяет не вводить дополнительный компонент инфраструктуры. Redis уже является зависимостью системы, его операционная стоимость уже учтена.

y-redis решает именно эту задачу: хранение авторитетного Y.Doc в Redis с синхронизацией через Pub/Sub. Использование готовой библиотеки снижает риски реализации по сравнению с написанием собственной логики синхронизации.

Задержка Redis Pub/Sub при локальном или сетевом развертывании составляет от 1 до 5 мс. Это не критично на фоне требования p95 < 100 мс для доставки обновлений клиенту.

Pub/Sub Redis является fire-and-forget: если нода не была подписана в момент публикации, она не получит пропущенные обновления через канал. Это ограничение компенсируется: при восстановлении ноды она загружает актуальный снапшот из Redis-ключа, который всегда содержит накопленное состояние.

## Последствия

При отказе Redis все ноды Realtime Sync Service теряют возможность синхронизировать обновления между собой. Клиенты, подключенные к разным нодам, временно расходятся. После восстановления Redis ноды перезагружают снапшот и синхронизируются. Это ограничение допустимо в рамках уровня надежности MVP.

Количество активных Pub/Sub каналов равно числу активных сессий. При большом числе одновременных сессий необходимо мониторить количество подписчиков и память Redis.

## Риски

Redis Pub/Sub не гарантирует доставку при временной недоступности подписчика. Снижение риска: механизм восстановления через Redis-снапшот при переподключении ноды.

Использование одного инстанса Redis является единой точкой отказа для Pub/Sub и хранения снапшотов. Снижение риска для production: Redis Sentinel или Redis Cluster. Для MVP допустим одиночный инстанс с мониторингом доступности.

## Оценка результативности

Распределение обновлений считается корректно реализованным, если при тестировании с двумя нодами Realtime Sync Service и клиентами, подключенными к разным нодам, CRDT-обновления доставляются всем участникам сессии в рамках требования p95 < 100 мс.
