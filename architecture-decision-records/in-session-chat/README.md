# Чат на онлайн-занятии: поверх Yjs (CRDT) с зеркалированием в PostgreSQL

Дата создания: 16.06.2026
Статус: Предложено

## Контекст

На экране «Онлайн-занятие» всем участникам нужен текстовый чат. Формально в функциональных требованиях ТЗ чат не выделен, но он необходим для полноценного занятия и согласуется с целью «единая среда вместо нескольких разнородных инструментов». Уже существует надёжный канал реального времени для сессии — Y.Doc на Realtime Sync (CRDT, WebSocket, репликация через Redis Pub/Sub, офлайн-устойчивость, снапшоты). Заводить под чат отдельный транспорт нежелательно.

Требования: доставка сообщений в реальном времени всем участникам, устойчивость к разрыву связи (сообщения не теряются), история чата после перезахода, возможность модерации.

## Рассмотренные варианты

**Отдельный WebSocket/HTTP-канал для чата.** Дублирует уже имеющийся real-time транспорт, требует своей логики переподключения и доставки, отдельной интеграции с Redis для мульти-ноды. Избыточно.

**Только БД + polling/REST.** Простая история, но нет «живой» доставки без дополнительного канала; противоречит ощущению реального времени.

**Чат как разделяемый тип в Y.Doc (`Y.Array('chat')`).** Сообщения едут по тому же CRDT-каналу, что и код: автоматическая рассылка всем, репликация между нодами через существующий Redis Pub/Sub, офлайн-буферизация и попадание в снапшот «бесплатно». История кратковременная (живёт в Y.Doc активной сессии). Долгая история и модерация требуют отдельного хранилища.

## Решение

Чат реализуется как **`Y.Array('chat')` в Y.Doc сессии** для доставки в реальном времени, с **зеркалированием в таблицу `chat_messages` (PostgreSQL)** для постоянной истории и модерации.

- Клиент добавляет сообщение `{ id, authorId, authorName, body, createdAt }` в `Y.Array('chat')`; рассылка всем участникам и репликация между нодами идут по уже существующему каналу Yjs/Redis.
- Realtime Sync в хуке `onUpdate` (тот же, что используется для снапшотов и анализа кода) детектит новые элементы чата и пишет их в `chat_messages` (идемпотентно по `id` сообщения).
- При входе в занятие клиент подгружает последнюю историю через `GET /api/sessions/:id/chat` (API Gateway), затем продолжает в реальном времени через Y.Doc.
- Системные сообщения (вход/выход участника, старт записи и т. п.) пишутся с `kind = SYSTEM`.

## Обоснование

Переиспользование Y.Doc даёт доставку в реальном времени, мульти-нодовую репликацию и офлайн-устойчивость без новой инфраструктуры — те же гарантии, что уже выполнены для кода. Зеркало в PostgreSQL закрывает то, чего нет у эфемерного Y.Doc: долгую историю, поиск и модерацию. Разделение «горячий путь — Yjs, долгое хранение — Postgres» повторяет уже принятый в проекте принцип (снапшоты Y.Doc в Postgres, рабочая копия в памяти/Redis).

## Последствия

В схему БД добавляется таблица `chat_messages` (см. ADR/доку по схеме). Realtime Sync получает обязанность зеркалировать чат в БД — это связывает BC-1 с хранилищем BC-3; запись выполняется асинхронно и не блокирует доставку. Размер Y.Array('chat') ограничивается (например, последние N сообщений в активном документе), полная история живёт в БД.

## Риски

Рост Y.Doc за счёт длинной переписки увеличивает размер снапшота. Снижение риска: хранить в Y.Array только хвост (последние N), остальное — в БД и подгружать по запросу.

Дублирование записи (Yjs у всех + строка в БД) требует идемпотентности по `id` сообщения, чтобы при репликации между нодами не возникли дубли в `chat_messages`.

## Оценка результативности

Решение считается корректным, если сообщение доставляется всем участникам в реальном времени по тому же каналу, что и код; после перезахода история восстанавливается из `GET /api/sessions/:id/chat`; при кратковременном разрыве связи отправленные сообщения не теряются (доезжают из Y.Doc), а в `chat_messages` нет дублей.
