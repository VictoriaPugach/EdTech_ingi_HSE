# Видеосвязь на онлайн-занятии: SFU (LiveKit) вместо P2P-mesh

Дата создания: 16.06.2026
Статус: Предложено

## Контекст

Экран «Онлайн-занятие» объединяет в одном окне совместное редактирование кода (CRDT), чат и видеосвязь участников. Видеосвязь в техническом задании прямо не зафиксирована как функциональное требование — она упомянута в разделе «Проблема» ТЗ как боль (для одного занятия преподаватель и ученики вынуждены использовать отдельный инструмент видеосвязи). Цель решения — убрать эту зависимость от внешних сервисов.

Нагрузка: типичное занятие — 1 преподаватель и 2–12 учеников. Одновременно работает несколько параллельных занятий (несколько сессий). Ключевое ограничение — экономия трафика: при большом числе участников и нескольких параллельных сессиях объём видеоданных растёт быстро, а часть пользователей сидит на слабых каналах. Требование к задержке наследуется от остальной системы: «живое» ощущение без заметных лагов.

## Рассмотренные варианты

**P2P-mesh (полносвязная сеть WebRTC).** Каждый участник устанавливает прямое соединение с каждым и отправляет свой поток N−1 раз. Не требует медиасервера, но исходящий трафик и нагрузка на CPU клиента растут линейно с числом участников. Для 12 участников каждый клиент отдаёт 11 копий своего видео вверх — это прямо противоречит требованию экономии трафика и не подходит для детских устройств и слабых каналов.

**MCU (микширование на сервере).** Сервер сводит все потоки в один и отдаёт каждому клиенту единый видеомикс. Минимальный трафик и CPU на клиенте, но очень дорого по CPU на сервере (транскодирование) и теряется гибкость раскладки. Для нескольких параллельных сессий стоимость серверных ресурсов неприемлема.

**SFU (Selective Forwarding Unit).** Каждый участник отправляет свой поток на сервер один раз; сервер выборочно пересылает потоки подписчикам. Исходящий трафик клиента не зависит от числа участников. В сочетании с simulcast/SVC сервер отдаёт каждому подписчику только тот слой качества, который тот способен принять. Это лучший компромисс «трафик / задержка / стоимость» для групповых занятий.

Среди SFU рассмотрены mediasoup, Jitsi Videobridge и LiveKit:
- **mediasoup** — самый экономичный по CPU (500–1000 участников на воркер), но это библиотека: сигналинг, управление треками и кластеризацию пишем сами. Высокая стоимость разработки.
- **Jitsi Videobridge** — зрелый полнофункциональный стек, но тяжелее в эксплуатации и менее удобные SDK для встраивания в собственный UI.
- **LiveKit** — современный open-source SFU (Apache-2), simulcast + adaptive subscriber track control, готовые клиентские SDK, кластер координируется через **Redis** (уже используется в проекте для CRDT Pub/Sub). Self-host без привязки к облаку.

## Решение

Видеосвязь реализуется через **SFU LiveKit (self-hosted)**.

- Каждый участник публикует медиа один раз; раздачу подписчикам выполняет SFU.
- Включается **simulcast** (публикуется 2–3 слоя качества) и **adaptive stream / dynacast**: SFU отдаёт каждому подписчику слой под его канал и размер плитки, а неиспользуемые слои не пересылает. Активный спикер получает высокий слой, плитки-превью — низкий.
- Кластеризация LiveKit использует **тот же Redis**, что и Realtime Sync (отдельные ключи/каналы). Любой участник подключается к любой ноде; медиа маршрутизируется между нодами кластера.
- Доступ к комнате — по короткоживущему **access-токену LiveKit**, который выпускает API Gateway после проверки JWT и роли пользователя (HOST/EDITOR/VIEWER). Realtime Sync (CRDT) остаётся отдельным каналом и не смешивается с медиа.
- Поведение по умолчанию для экономии трафика: камера-превью ограничена по разрешению (≈360p), для не-говорящих видео может ставиться на паузу, доступен режим «только аудио». Кодек — VP8/VP9 (SVC) с возможностью перехода на AV1.

## Обоснование

SFU — единственный из трёх вариантов, у которого исходящий трафик клиента не зависит от числа участников; это прямо отвечает требованию экономии трафика при многих людях и параллельных сессиях. MCU отвергнут из-за стоимости транскодирования на сервере, mesh — из-за квадратичного роста клиентского трафика.

LiveKit выбран среди SFU, потому что: (1) кластер координируется через Redis, который уже в инфраструктуре проекта, — минимум новой инфраструктуры; (2) simulcast + adaptive track control дают именно ту экономию трафика, что требуется, без ручной реализации; (3) готовые SDK снижают объём фронтенд-кода; (4) Apache-2 и self-host соответствуют требованию ТЗ о технологической независимости от внешних сервисов. mediasoup эффективнее по CPU, но цена — самостоятельная реализация сигналинга и управления треками, что несоразмерно для текущего этапа.

Сигналинг WebRTC не нагружается на собственный WebSocket Realtime Sync (он остаётся бинарным каналом Yjs sync/awareness) — за сигналинг и медиа отвечает LiveKit, что сохраняет разделение ответственности между BC.

## Последствия

Появляется новый инфраструктурный компонент — медиасервер LiveKit (отдельный деплой, порты UDP/TCP, при необходимости TURN-сервер для NAT-traversal в сетях учебных заведений). API Gateway получает обязанность выпускать access-токены LiveKit на основе роли участника.

Состояние камеры/микрофона эфемерно и хранится в LiveKit/awareness, а не в БД. В реляционной БД для видео таблицы не заводятся (см. ADR по схеме). Запись занятий в MVP не предусмотрена.

## Риски

UDP-трафик WebRTC может блокироваться в сетях учебных заведений. Снижение риска: TURN over TCP/TLS на 443 как fallback.

Эксплуатация отдельного медиасервера повышает операционную сложность. Снижение риска: на старте — один узел LiveKit на dev/prod, горизонтальное масштабирование через Redis по мере роста числа сессий.

Простой LiveKit Cloud не используется, чтобы не вводить зависимость от внешнего провайдера; вся обработка остаётся self-hosted.

## Оценка результативности

Решение считается корректным, если при 1 преподавателе и до 8 учениках в сессии исходящий трафик клиента не растёт с числом участников (подтверждается метриками publish-битрейта), подписчики на слабом канале автоматически получают пониженный слой без разрыва аудио, а несколько параллельных сессий работают на одном узле LiveKit без деградации задержки.
