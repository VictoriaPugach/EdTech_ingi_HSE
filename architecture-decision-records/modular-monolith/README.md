# Выбор модульного монолита как архитектурного стиля

Дата создания: 12.12.2025
Статус: Принято

## Контекст

Платформа состоит из трех логически различных областей: совместное редактирование кода с CRDT-синхронизацией, педагогический анализ и генерация подсказок, управление пользователями и сессиями. Каждая область имеет собственные требования к производительности и технологии. Realtime Sync Service должен масштабироваться горизонтально при росте числа одновременных сессий. Hint Service содержит Python-зависимости (Tree-sitter) и не может быть запущен в среде Node.js. Работа ведется малой командой, прототип должен быть реализован в рамках одного учебного проекта.

## Рассмотренные варианты

Классический монолит объединил бы весь код в одном процессе. Python-компонент для AST-анализа не может исполняться в одном рантайме с Node.js без IPC-прослойки. Монолит также создает риск неконтролируемых зависимостей между модулями по мере роста кодовой базы.

Полная микросервисная архитектура предполагает самостоятельный деплой каждого сервиса, собственное хранилище, оркестрацию, трассировку и управление межсервисными контрактами. Для команды из одного-двух разработчиков на этапе MVP это создает непропорциональные операционные издержки.

Модульный монолит с изолированными сервисами объединяет модули с четкими интерфейсами в одном репозитории при разных рантаймах. Каждый модуль деплоится как отдельный контейнер, но не имеет собственной базы данных. Взаимодействие между контейнерами происходит через API Gateway, а не через прямые внутренние вызовы между доменными моделями.

Serverless-подход не подходит для WebSocket-соединений с долгим временем жизни и CRDT-состоянием в памяти.

## Решение

Система реализована как модульный монолит с разделением по рантаймам. Выделены три контейнера: Realtime Sync Service на Node.js, Hint Service на Python, API Gateway/LMS на Node.js. Общее хранилище данных PostgreSQL разделяется между контейнерами, но каждый контекст работает только со своими таблицами. Redis используется Realtime Sync Service для Pub/Sub и кэширования. Frontend является статическим SPA, раздаваемым через Nginx.

Структура репозитория monorepo: каждый контейнер расположен в собственной директории с независимым package.json или requirements.txt и независимым Dockerfile.

## Обоснование

Разные рантаймы для разных задач обоснованы технически. Node.js с event loop оптимален для большого числа одновременных WebSocket-соединений с минимальным I/O-ожиданием. Python обеспечивает доступ к Tree-sitter через нативные биндинги и к библиотекам обработки AST. Попытка запустить Tree-sitter Python-биндинги в Node.js потребовала бы обходных решений или потери надежности.

Модульный монолит сохраняет управляемость проекта. Разработчик может запустить всю систему одной командой через Docker Compose без необходимости настраивать service mesh или сложную оркестрацию. Это ускоряет итерацию при разработке и отладке.

Изоляция доменных моделей между контекстами достигается организационно: в рамках каждого контейнера применяются принципы DDD, прямых импортов типов между контейнерами нет, взаимодействие только через REST или события.

Архитектура готова к эволюции. Если после MVP появится необходимость масштабировать Hint Service независимо или добавить отдельное хранилище для аналитики, каждый контейнер уже является самостоятельным деплоем с изолированными зависимостями.

## Последствия

Общая база данных PostgreSQL является компромиссом относительно полной микросервисной изоляции. Если в будущем возникнет необходимость разделить хранилища, потребуется миграция схемы. На этапе MVP это принятое ограничение, позволяющее избежать saga-паттернов и распределенных транзакций.

Отсутствие строгих гарантий сетевой изоляции между контейнерами на уровне Kubernetes не критично, так как все три контейнера относятся к одному приложению и деплоятся в одном namespace.

## Риски

Основной риск: при неконтролируемом росте количества зависимостей модульный монолит может деградировать в неструктурированный монолит. Снижение риска: обязательные code review на предмет нарушения границ контекстов, запрет прямых импортов типов между директориями разных контекстов.

## Оценка результативности

Архитектурный стиль считается корректно реализованным, если каждый контейнер может быть собран, протестирован и запущен независимо, и если анализ зависимостей не выявляет прямых импортов между доменными моделями разных ограниченных контекстов.
