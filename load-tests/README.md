# Нагрузочные тесты

Сценарии для проверки целевых показателей производительности из тест-плана:

| Тест | Файл | Критерий приёмки |
|------|------|------------------|
| Hint Service под нагрузкой | `hint-api.k6.js` / `hint-api.mjs` | TC-08 / AC-03: **p95 < 2000 мс** при 20 пользователях |
| Задержка совместного редактирования | `ws-latency.mjs` | TC-04 / AC-02: **p95 < 100 мс** распространения правки |

> Это **измерительные** скрипты — они дают фактические числа p50/p95/p99, которых
> раньше в проекте не было (в тексте фигурировали только целевые пороги).

---

## 0. Поднять сервисы локально

Тесты бьют по запущенным сервисам. Проще всего — dev-стек:

```bash
docker compose up -d
```

Должны слушать:
- Hint Service — `http://localhost:4002`
- realtime-sync — `ws://localhost:4001/ws` (в dev по умолчанию **без обязательного токена**)

---

## 1. Hint Service (TC-08, p95 < 2000 мс)

**Вариант без установки (Node 20+):**
```bash
node load-tests/hint-api.mjs
# параметры по желанию:
VUS=20 ITER=30 node load-tests/hint-api.mjs
```

**Вариант на k6** (как в тест-плане; нужен установленный [k6](https://k6.io/docs/get-started/installation/)):
```bash
k6 run load-tests/hint-api.k6.js
```

Оба бьют напрямую в Hint Service (без авторизации). На выходе — p50/p95/p99 и вердикт
PASS/FAIL относительно порога 2000 мс.

---

## 2. Задержка редактирования (TC-04, p95 < 100 мс)

```bash
node load-tests/ws-latency.mjs
# 5 комнат по 2 клиента = 10 соединений, 180 секунд:
PAIRS=5 DURATION=180 node load-tests/ws-latency.mjs
```

Скрипт использует настоящий клиент Yjs/`y-websocket` (зависимости проекта — запускайте
**из корня репозитория**). В каждой комнате писатель раз в 200 мс добавляет метку
времени в общий CRDT-массив, читатель ловит её — разница и есть сквозная задержка
клиент→сервер→клиент.

> Против **прод**-сервера (`wss://kidcoded.ru/ws`) тест не пойдёт «как есть»:
> там включён `REQUIRE_AUTH=true` и нужен сессионный токен. Меряйте на локальном
> dev-стеке либо временно поднимите realtime-sync с `REQUIRE_AUTH=false`.

---

## Как трактовать результат

- **PASS** — p95 ниже порога: показатель из тест-плана подтверждён фактическим замером.
- **FAIL** — p95 выше порога: приложите вывод к отчёту, это вход для оптимизации
  (профилирование Hint Service, настройка Redis fan-out, ресурсы контейнеров).

Числа зависят от машины. Для отчёта фиксируйте окружение: CPU/RAM, где крутятся
сервисы (локально / VPS), и параметры запуска (`VUS`, `PAIRS`, `DURATION`).
