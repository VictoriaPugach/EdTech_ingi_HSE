# Нагрузочное тестирование

## Нужно ли много людей? — Нет

Распространённое заблуждение: чтобы проверить «10 одновременных участников», якобы
нужно 10 живых тестировщиков. Это не так. **Нагрузочные скрипты сами эмулируют
много одновременных «виртуальных пользователей»** с одной машины: открывают N
параллельных соединений/запросов и измеряют задержки. Поэтому провести замер
может **один человек** (вы) — реальные ученики не требуются.

Целевые показатели (из тест-плана):
- **TC-04 / AC-02**: p95 задержки распространения правки < **100 мс** при 10 участниках;
- **TC-08 / AC-03**: p95 времени ответа Hint Service < **2000 мс** при 20 запросах.

## Какие сценарии есть

| Сценарий | Файл | Где запускать |
|----------|------|---------------|
| Hint Service напрямую | `load-tests/hint-api.mjs` / `.k6.js` | локально |
| Hint Service через прод (Caddy→gateway→hint) | `load-tests/hint-api-prod.mjs` | против сервера |
| Задержка совместного редактирования | `load-tests/ws-latency.mjs` | локально |

Все запускаются из **корня репозитория** на Node 20+ (ничего ставить не нужно).

---

## Вариант A. Локально (проще всего, рекомендуется для отчёта)

Даёт чистые числа без влияния интернет-канала.

```bash
docker compose up -d                 # поднять dev-стек (hint :4002, realtime :4001)
node load-tests/hint-api.mjs         # p95 Hint Service
node load-tests/ws-latency.mjs       # p95 задержки редактирования (10 соединений)
```

Замеренные значения (локально, всё в Docker на одной машине):
- Hint Service: **p95 ≈ 38 мс** (порог 2000) — 600 запросов, 0 ошибок;
- Задержка редактирования: **p95 ≈ 1 мс** (порог 100) — 10 соединений.

## Вариант B. Против сервера (прод)

### Hint Service — работает «как есть»

Бьёт по публичному `https://kidcoded.ru/api/hints` (полный путь через Caddy и
gateway). Скрипт сам заводит служебный аккаунт и логинится для JWT.

```bash
node load-tests/hint-api-prod.mjs
# параметры: BASE=https://kidcoded.ru VUS=20 ITER=30 node load-tests/hint-api-prod.mjs
```

Замер против прода: **p95 ≈ 125 мс** (порог 2000) — 600 запросов, 0 ошибок, ~142 req/s.
Здесь в задержку уже входит реальный интернет-канал — потому больше локальных 38 мс,
но всё равно далеко в пределах нормы.

### Задержка редактирования (WS) — пока только локально

В проде realtime-sync включён в защищённом режиме (`REQUIRE_AUTH=true`): каждое
WS-подключение требует сессионный токен (его выдаёт `POST /api/sessions/:id/join`).
Поэтому простой скрипт `ws-latency.mjs` (анонимный) к проду не подключится.

Варианты:
1. **Мерить локально** (как в варианте A) — рекомендуется для отчёта: показывает
   время обработки сервером и Redis-fan-out без влияния канала.
2. Доработать скрипт под прод: для каждого «участника» сначала вызывать join и
   подключаться с `?token=` — отнесено к следующему этапу.

---

## Что зафиксировать в отчёте

Числа зависят от окружения, поэтому для воспроизводимости укажите:
- где крутились сервисы (локально в Docker / на VPS), CPU/RAM машины;
- параметры запуска (`VUS`, `ITER`, `PAIRS`, `DURATION`);
- вывод скрипта (p50/p95/p99) и вердикт PASS/FAIL.

> Эти замеры закрывают целевые критерии AC-02/AC-03 фактическими числами. Полное
> испытание при 10 живых участниках и экспертная оценка подсказок отнесены к
> следующему этапу (см. `docs/prototype-limitations.md`).
